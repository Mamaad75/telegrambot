# Data and privacy policy

What this platform collects, what it deliberately does not, and how that is enforced in
code rather than by convention.

## What is collected

**Publicly available business information only:**

- business name, category, address, coordinates
- publicly published phone numbers and e-mail addresses
- business websites and their publicly served pages
- public social profile URLs
- publicly displayed review counts and ratings
- publicly advertised services and products, opening hours

**First-party Baimar data**, when an administrator connects the account:

- Baimar's own Google Ads search terms and campaign performance
- Baimar's own Search Console queries for Baimar-owned properties

**Data the team enters**: notes, call outcomes, tasks, follow-ups, pipeline status.

## What is never collected

There is **no code path** in this repository that collects, requests or stores:

- private search history, or any individual person's search activity
- private Google, social or e-mail account data
- passwords, session cookies or authentication tokens belonging to third parties
- payment or financial data
- personal data about individuals who are not business contacts
- content behind a login, a paywall, or a CAPTCHA

## Things the platform refuses to do

- **No CAPTCHA bypassing.** A CAPTCHA is an answer, and the answer is no.
- **No authentication bypass.** Only publicly served pages are read.
- **No anti-bot evasion.** The crawler sends one honest, contactable user agent and does
  not rotate identities, spoof browsers, or use residential proxies.
- **No stolen sessions or cookies.**
- **No unauthorised private-data collection.**

## The distinction the UI is built to preserve

Search-demand data is **aggregate**. The platform can say:

> "A demand signal for e-commerce websites was detected in Arak: 2,890 impressions and
> 143 clicks across 3 observations from Google Ads and imported keyword research."

It can never say, and no data source connected to it could support:

> ~~"Person X searched for 'website design' yesterday."~~

Every market figure carries its basis and its sources. Below `minSampleSize` observations
the answer is **INSUFFICIENT_DATA** with the reason, not an estimated number.

This is stated in the product, not only here: the Market page carries a permanent,
non-dismissible notice saying that the platform cannot identify who searched for anything,
and listing the four sources it does use. The campaign-signal table repeats it directly
above the data.

### Search volume is never invented

A number is only printed when a source reported one. The four possible states are
distinct and all four reach the UI:

| State | Meaning | Shown as |
| --- | --- | --- |
| `REPORTED` | A provider returned an absolute volume | the number |
| `IMPORTED` | A human uploaded it in a CSV | the number, labelled "imported" |
| `RELATIVE_SIGNAL` | We can see demand (impressions, clicks) but not its absolute size | "relative signal only" |
| `UNKNOWN` | No volume data at all | "unknown" — never `0` |

The difference between `UNKNOWN` and `0` is the whole point. Zero means "we measured and
found none"; unknown means "nobody measured". Printing the first when we mean the second
is the most common way a tool like this misleads the person using it.

Every record is tagged with its origin so the two can never be confused:

| Origin | Meaning |
| --- | --- |
| `PUBLIC_BUSINESS_RESEARCH` | Public information about a business |
| `FIRST_PARTY_BAIMAR` | Baimar's own analytics and Search Console |
| `ADVERTISING_CAMPAIGN` | Baimar's own advertising performance |
| `AGGREGATE_SEARCH_SIGNAL` | Aggregate keyword/demand data |
| `AI_INFERENCE` | Generated by a language model |
| `MANUAL_ENTRY` | Entered by a Baimar user |

## Crawling conduct

- Identified user agent with a contact URL.
- `robots.txt` fetched, cached and obeyed; `Disallow` means we do not fetch. A 401 or 403
  on `robots.txt` is read as "disallow everything" — the cautious interpretation.
- `Crawl-delay` honoured when it exceeds our own throttle.
- One request per host at a time, with a configurable minimum gap.
- Hard caps on bytes, pages and time per site.
- Only publicly served pages; no forms submitted, no logins attempted, nothing written.

A site that blocks us is recorded as "blocked by robots.txt" and left alone. The lead is
still scored on everything else known about it.

## Honesty in the product

The commercial temptation in a tool like this is to fill gaps with plausible numbers. The
platform is built to resist that:

- Missing data renders as **Unknown** / **Not found** / **Needs verification**, never as
  zero and never as a placeholder value.
- The website audit reports **which checks it could not perform**. It does not run
  Lighthouse, so it never reports Core Web Vitals.
- A website URL discovered by guessing is stored as **NOT_VERIFIED** until a human
  confirms it, and the sales brief says so.
- Business value is a coarse tier from public signals, explicitly **not revenue**.
- Technology detection reports its evidence and a confidence level; it never claims
  certainty about a heuristic.
- AI output is stored and displayed as `AI_INSIGHT`, with a standing note that it must be
  checked against the observed data before being quoted to a customer.
- Demo data is flagged in the database, prefixed `[نمونه]`, uses RFC 2606 reserved domains,
  and is excluded from production views by default.

## Data subject requests

Business contact information held here is public business data. If a business asks to be
removed:

1. Find the lead (search by name, phone or domain).
2. Archive it (Delete on the lead — it archives rather than deletes, so the removal itself
   stays auditable).
3. To erase it entirely, delete the row; cascading deletes remove its audits, signals,
   scores, briefs and CRM history.
4. Add the domain to the crawler's exclusion list so discovery does not re-add it.

The audit log records who performed the removal and when.
